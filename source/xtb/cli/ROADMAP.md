# `xtb.cli` Roadmap

This is the living design and implementation queue for `xtb.cli`.

A feature appearing here is **not** approval to implement it. The intended
workflow is to discuss each item, decide whether it belongs in the library,
settle the API/semantics, mark it approved, and only then implement it.

Features are ordered by current importance, not implementation cost.

## Status vocabulary

- **done** — implemented, reviewed, and tested;
- **proposed** — useful enough to discuss, not yet approved;
- **discussing** — actively being designed;
- **approved** — design accepted and ready to implement;
- **in progress** — implementation underway;
- **deferred** — useful, but deliberately postponed;
- **rejected** — intentionally outside the library.

For roadmap changes, preserve these project constraints:

- `-betterC`, `nothrow`, `@nogc`;
- no GC, exceptions, runtime registration, or `TypeInfo` dependency;
- compile-time rejection of invalid static schemas;
- explicit ownership/allocation;
- borrowed input where possible;
- no callbacks for command dispatch;
- keep parser semantics independent of terminal/environment policy;
- prefer field/type semantics over redundant attributes;
- test feature combinations, not just isolated happy paths.

# Implemented foundation

## Typed static command tree — done

**Importance:** foundational

Structs define commands, `CliCommands!(...)` defines children, and
`ParsedCommand!T.command!Child` provides typed traversal. Exactly one child is
active at each command level.

**Keep:** application dispatch as ordinary D control flow; do not add runtime
command registries or callback dispatch.

## Derived requiredness and defaults — done

**Importance:** foundational

Ordinary value-taking scalar `T` fields are required by default. `Option!T`
preserves absence. `cliDefault` uses the initialized semantic value and
`cliDefaultInput` parses a fallback spelling at runtime. `cliRequired` has been
removed.

`cliHideDefault` explicitly suppresses default visualization without changing
runtime behavior.

**Keep:** do not infer defaults from whether a D field initializer happens to
differ from `.init`.

## Intrinsic zero-occurrence argument categories — done

**Importance:** foundational

Presence flags, count flags, repeated arrays/rest values, and terminal triggers
have natural zero-occurrence semantics and are omittable without `Option`.
A plain negatable `bool`, by contrast, is an explicit two-way scalar choice and
is required unless it is `Option!bool` or has a default.

## Custom CLI value representations — done

**Importance:** high

`cliValueWith!Representation` groups a required static `parse` operation with an
optional static `format` operation. Allocator requirements and whole-field vs
element parsing are inferred from the parse signature.

**Keep:** custom default input is validated at runtime; do not require custom
parsers to be CTFE-capable.

## Named/positional/repeated/rest parsing — done

**Importance:** foundational

Named values, fixed positionals, optional `Option!T` positionals, repeated
`Array!T`, `cliRest`, short clusters, attached short values, `--name=value`, and
`--` are supported.

## Nested commands and inherited globals — done

**Importance:** foundational

Nested `CliCommands` and `cliGlobal` are supported with compile-time collision
validation across the subtree.

## Built-in help/version controls — done

**Importance:** high

Built-in `-h`/`--help` and root `--version` are generated by default and may be
independently disabled with `cliNoBuiltinHelp` / `cliNoBuiltinVersion`.

## Public generated help — done

**Importance:** high

`writeHelp!(Root, Path...)` renders root or compile-time selected descendant
help independently of parser interception.

## Canonical-first rich help and ANSI rendering — done

**Importance:** high

Help renders canonical spellings first. Required named options are structural:
they appear explicitly in `Usage:` and in `Required options:` /
`Required global options:` sections, while omittable options remain under
`Options:` / `Global options:`. Aliases, negation, values, and defaults stay as
secondary metadata. ANSI emission is explicitly selected by the caller and uses
the generic core `AnsiWriter`; TTY/`NO_COLOR` policy remains outside `xtb.cli`.

## Option and command aliases — done

**Importance:** high

Long/short option aliases and command aliases are accepted as spellings of one
logical field/command. Canonical names remain diagnostic/help identity.

## Negatable booleans — done

**Importance:** high

`cliNegatable` supports `--name` / `--no-name` without `--flag=true` syntax and
composes with `Option!bool` and semantic defaults.

## Missing-subcommand policies — done

**Importance:** high

`cliSubcommandOptional` and `cliHelpOnNoSubcommand` cover the useful non-error
behaviors when argv ends before a child command is selected.

## Terminal arguments — done

**Importance:** high

`cliTerminal` is an optional application-defined trigger that stores its value,
stops parsing, and exposes the partial typed tree without parser callbacks.

## Hidden arguments — done

**Importance:** medium

`cliHidden` keeps an argument parseable while omitting it from generated help.
Hidden arguments must be omittable, preventing required-but-undiscoverable
schemas.

# Ranked future work

## 1. Required parent positionals before subcommands

**Status:** proposed
**Importance:** very high

### Why

This is the largest remaining structural limitation. Common CLIs naturally put
a resource identifier before an operation:

```text
tool <WORKSPACE> build
tool <WORKSPACE> test
cloud <PROJECT> deploy
```

Today a command with child commands cannot declare any positional fields.

### Proposed interface

No new attribute should be necessary:

```d
struct RootArgs
{
    @(cliPositional, cliValueName("WORKSPACE"))
    String workspace;

    alias Commands = CliCommands!(BuildArgs, TestArgs);
}
```

### Proposed semantics

Initially permit only **fixed required** parent positionals before subcommand
selection.

Allow:

```text
tool <WORKSPACE> <COMMAND>
tool <ORG> <PROJECT> <COMMAND>
```

Continue to reject optional, repeated, or rest parent positionals because they
make the command boundary ambiguous.

Required parent positionals are consumed first. Only after they are complete
does a bare token participate in child-command matching. Therefore, if
`<PROJECT>` is required, `tool build` means `PROJECT="build"` followed by a
missing command. This preserves the ability to name a project `build`.

### Implementation thoughts

- Relax the blanket positional/subcommand schema assertion only for a proven
  fixed-required prefix.
- Parse that prefix before child matching.
- Preserve named/global option handling around it.
- Update selected/static usage to include ancestor positionals.
- Finalize parent defaults/requiredness before declaring the invocation valid.
- Test aliases, globals, `--`, built-in help, terminal outcomes, and both
  missing-position/missing-command diagnostics.

### Recommendation

**Undertake.** High value, deterministic if kept to the strict form above.

## 2. Argument relationships and groups

**Status:** proposed
**Importance:** very high

### Why

Real CLIs frequently need constraints that field types cannot express:

```text
--quiet conflicts with --verbose
--pretty requires --output
exactly one of --file / --stdin
at least one of --include / --exclude
```

Doing this entirely in application code duplicates presence bookkeeping and
cannot contribute generated diagnostics/help.

### Proposed interface

Use compile-time logical field references, never option spellings:

```d
@(cliConflictsWith!"stdout")
Option!String output;

bool stdout;
```

```d
@(cliRequires!"output")
bool pretty;
```

For n-ary constraints, prefer type-level declarations:

```d
@cliGroup!(CliGroupRule.exactlyOne, "file", "stdin")
struct Args
{
    Option!String file;
    bool stdin;
}
```

Names are provisional.

### Semantics

Relations should be based on **explicit CLI presence**, not final stored values
or defaults. `--no-color` and `--color` both count as presence of the same
logical field. Aliases do likewise.

Initial rules should be limited to conflicts, requires, at-most-one,
at-least-one, and exactly-one. Avoid arbitrary boolean-expression DSLs.

### Implementation thoughts

- Reuse per-field `seen` bookkeeping.
- Compile-time validate referenced fields and impossible/redundant groups.
- Validate after defaults/required scalar completion but before returning a
  normal invocation.
- Skip relation validation on terminal/built-in outcomes.
- Add dedicated `CliErrorKind` values and help metadata where useful.

### Recommendation

**Undertake after parent positionals.** This eliminates a large amount of
application-side validation without making the parser dynamic.

## 3. Better diagnostics and typo suggestions

**Status:** proposed
**Importance:** high

### Why

Unknown options/commands are common user mistakes, and the schema already knows
all valid spellings.

Desired behavior:

```text
error: unknown option '--verbsoe'
       did you mean '--verbose'?
```

and similarly for child commands.

### Proposed interface

No schema API is necessary initially. Suggestions should be an automatic
property of generated diagnostics.

Possibly add a render option later to disable suggestions in machine-oriented
output.

### Implementation thoughts

- Use a small allocation-free edit-distance or bounded similarity routine over
  compile-time-known spellings.
- Prefer canonical spellings in suggestions even when an alias happens to be
  equally close.
- Keep a conservative threshold; a bad suggestion is worse than no suggestion.
- Never change parsing based on similarity.
- Add tests for short names, long aliases, negative spellings, nested commands,
  and inherited globals.

### Recommendation

**Undertake.** High user-facing value with little API surface.

## 4. Generated shell completions

**Status:** proposed
**Importance:** high

### Why

The static schema already contains most information needed for Bash, Zsh, Fish,
and possibly PowerShell completion: commands, aliases, options, value-taking
behavior, enum/possible values, and descriptions.

### Proposed interface

Prefer a rendering API rather than automatic installation:

```d
writeCompletion!Args(writer, CliShell.bash, programName);
```

A CLI can expose it through an application-owned terminal argument:

```d
@(cliTerminal, cliValueName("SHELL"))
CompletionShell completions;
```

### Implementation thoughts

- Keep completion generation separate from parsing.
- Generate from the same schema traits used by help.
- Support enum and `cliPossibleValues` value completion first.
- Do not invent dynamic filesystem/network completion callbacks in the first
  version.
- Hidden fields should remain hidden from generated completions by default.

### Recommendation

**Undertake.** Common capability and a strong fit for a static schema.

## 5. Help wrapping and rendering options

**Status:** proposed
**Importance:** high-medium

### Why

The canonical-first layout is readable, but long descriptions/possible-value
lists can exceed terminal width.

### Proposed interface

Keep the default deterministic and environment-independent:

```d
CliHelpOptions options;
options.width = 100;
options.ansi = true;

writeHelp!Args(writer, programPath, options);
```

The exact options type should be discussed; do not make `writeHelp` inspect the
terminal itself.

Likely useful knobs:

- maximum width / no wrapping;
- ANSI enabled;
- perhaps whether aliases/default metadata are shown.

Avoid a large theming system unless a real use case appears.

### Implementation thoughts

- Wrap descriptions/metadata based on visible width, not ANSI byte count.
- Preserve canonical label alignment until doing so becomes unreasonable, then
  place the description on a continuation line.
- Never allocate solely to wrap help.

### Recommendation

**Undertake eventually.** Useful polish, but lower priority than parser/schema
capabilities.

## 6. Common value constraints

**Status:** proposed
**Importance:** medium-high

### Why

Custom parsers can validate anything, but simple constraints such as numeric
ranges are common enough that forcing a custom representation is noisy.

Potential examples:

```d
@cliRange!(1, 64)
uint jobs;

@cliOneOf!("debug", "release")
String profile;
```

`cliPossibleValues` is currently help-only and must remain so unless a separate
validation concept is deliberately introduced.

### Proposed direction

Prefer a very small set of strongly typed validators rather than a generic
runtime callback API. Numeric min/max or range is the strongest candidate.

For string/enumerated domains, custom `cliValueWith` or enums may already be
good enough; avoid duplicating them without evidence.

### Implementation thoughts

- Validation occurs after parsing the field value.
- Constraints should contribute meaningful diagnostics and, where truthful,
  generated help.
- Compile-time reject constraints incompatible with the field type.

### Recommendation

**Discuss after relationships.** Useful, but custom parsers already cover the
problem and may be sufficient.

## 7. Environment-variable fallback

**Status:** proposed
**Importance:** medium

### Why

Many non-trivial CLIs allow values such as credentials, profiles, cache paths,
or endpoints to come from environment variables.

### Major architectural concern

`xtb.cli` currently does not own environment/OS policy. Directly calling
`getenv` from the parser would introduce a new ambient input source and couple
the core parser to OS behavior.

### Possible interface

A schema declaration could exist:

```d
@cliEnv("MY_TOOL_TOKEN")
Option!String token;
```

but parsing should probably require an explicitly supplied environment lookup
provider rather than silently reading process state.

Precedence would need to be explicit, likely:

```text
CLI input > environment > declared default > absence/error
```

### Implementation thoughts

- Keep environment access injectable and testable.
- Preserve borrowed lifetime or copy deliberately when environment storage
  cannot satisfy the result lifetime.
- Decide whether environment-derived values count as explicit presence for
  future relationship/group rules; my preference is **no**, unless a relation
  is explicitly defined over resolved values rather than argv presence.
- Help may show the environment variable name but should not expose its current
  value.

### Recommendation

**Useful but defer until the precedence/presence model is settled.** Do not
casually add ambient environment reads to the parser.

## 8. Hidden subcommands

**Status:** proposed
**Importance:** medium

### Why

`cliHidden` currently applies to fields. Some applications also need legacy,
experimental, or internal subcommands that remain parseable but are omitted
from help/completion listings.

### Proposed interface

Potentially allow the existing attribute on command types:

```d
@(cliCommand("internal"), cliHidden)
struct InternalArgs
{
}
```

### Semantics

- still parse by canonical name and aliases;
- still participate in collision validation;
- omitted from command listings and generated completion by default;
- explicit static `writeHelp!(Root, InternalArgs)` should probably still render
  the command's own help, because the caller explicitly requested it.

### Recommendation

**Probably worthwhile**, but not urgent.

---

## 9. Deprecation metadata for old spellings

**Status:** proposed
**Importance:** medium-low

### Why

Aliases are useful for migrations, but today an old alias is indistinguishable
from a permanent synonym.

Possible future shape:

```d
@cliDeprecatedAlias("old-name", "use --new-name")
```

or a more general spelling metadata type.

### Concerns

This adds warning/output policy and potentially machine-readable diagnostic
semantics. It should not be implemented merely because aliases exist.

### Recommendation

**Defer until a real compatibility migration needs it.**

---

## 10. Response files (`@args.txt`)

**Status:** deferred
**Importance:** medium-low

### Why

Response files are useful for compilers/linkers and extremely long command
lines, but they are not universal CLI behavior.

### Concerns

They introduce filesystem I/O, tokenization/quoting rules, recursion/cycle
handling, file encoding, and lifetime/ownership complexity.

### Recommendation

**Defer.** If implemented, it should likely be an input-source layer rather
than special cases spread through field parsing.

# Explicit non-goals / rejected scope

## Dynamic or external subcommands — rejected

`xtb.cli` is intentionally based on a statically known typed command tree.
Runtime plugin command discovery or Git-style external executable dispatch
would undermine that model and belongs at the application layer.

## Automatic environment/TTY policy inside rendering — rejected

The caller decides ANSI policy and passes it to CLI rendering. `xtb.cli` should
not call `shouldUseAnsi`, inspect `NO_COLOR`, or decide stdout/stderr terminal
capability itself.

## Callback-based command dispatch — rejected

Parsing returns data. Applications dispatch with ordinary typed control flow.

## Arbitrary validation expression DSL — rejected for now

Relationships should start with a small set of common statically validated
rules. Avoid growing a mini boolean language in attributes.

# Next discussion

The next feature to discuss is **required parent positionals before
subcommands**. Before implementation, settle:

1. exact interaction with `--`;
2. whether only plain required scalar positionals are allowed or whether
   required custom-representation positionals are equally valid;
3. how descendant help should present ancestor positional descriptions;
4. exact missing-positional versus missing-command diagnostics.
